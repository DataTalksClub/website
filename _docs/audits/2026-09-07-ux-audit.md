## Detailed findings and implementation instructions

### UX-01 — Studio confirmations are executable metadata, and several fail before asking

**Priority:** P0. **Confidence:** high; source plus Django-rendered browser execution. **Owners:** Studio Courses templates, one shared confirmation script, focused staff-action tests.

Evidence:

- `studio_courses/templates/studio_courses/_extend_deadline_menu.html:22` puts `title` and other values inside a quoted JavaScript `confirm` argument.
- `studio_courses/templates/studio_courses/homework_submissions.html:69`, `:78`, `:88`, `:98`, and `:107` repeat this for setting/clearing answers, scoring/rescoring, and sending notifications.
- `studio_courses/templates/studio_courses/course_admin.html:239`, `:245`, `:252`, `:260`, `:331`, and `:339` repeat the same interpolation for homework/project actions.
- `studio_courses/templates/studio_courses/project_submissions.html:77` and `:88` do the same for review assignment/scoring.
- `studio_courses/templates/studio_courses/enrollment_edit.html:181` starts a single-quoted JavaScript string that contains literal newlines through line 191. The parsed handler cannot compile.
- Homework/project titles are ordinary database text: `courses/models/homework.py:45`, `courses/models/project.py:53`. HTML escaping does not make text safe in JavaScript strings: the browser decodes entities before compiling an inline event handler.
- `core/middleware.py:52` allows inline scripts in the current CSP, so the CSP is not a defense for this interpolation.

Reproduction:

1. Render the deadline confirmation with an ordinary synthetic title containing an apostrophe. Compile the browser-parsed `onsubmit`; it raises a syntax error.
2. Render either branch of the LiP-disable confirmation. It raises a syntax error even with ordinary data because of the literal newlines.
3. The safe diagnostic also renders a title that contributes an expression inside the `confirm` argument. With `confirm` replaced by a no-op, the expression executes a boolean marker in the window. This proves script execution at the template boundary without executing an external payload.

Impact: score/deadline/email actions may proceed without their intended confirmation when the handler fails. If an attacker can influence a title that reaches one of these staff pages, the title is a stored-script execution surface in the staff origin. The audit proves the sink and normal database title path; it does not claim every unprivileged user can edit titles.

Fix, in order:

1. Inventory all `onsubmit`/`onclick` attributes that interpolate course, homework, project, person, or other display text. Include both course summary and detail templates so one cannot retain the defect.
2. Move the complete confirmation message into a normally escaped `data-confirm-message` attribute or server-rendered text node. Do not concatenate display text into executable JavaScript. Normal Django escaping is appropriate for a data attribute because the listener treats the resulting string as data.
3. Add one shared external listener loaded by the Studio Courses base. On submit, read `form.dataset.confirmMessage`; cancel the event when the user declines. Avoid duplicate listener registration and keep the action's existing POST payload and CSRF token.
4. For destructive score changes, use an explicit server-validated confirmation step/field if confirmation is required by the action contract. A browser confirm is a convenience, not server authorization; JS failure should not silently remove a required gate.
5. Remove the multiline handler and duplicate interpolation copies. Preserve the current capability checks, audit context, and idempotency semantics.

Acceptance tests:

- Render apostrophes, quotation marks, newlines, Unicode, and HTML-like title text; no script error or injected window marker occurs and the displayed confirmation message preserves the title as text.
- Accepting/declining the prompt produces exactly one/no POST, respectively. Existing POST/CSRF/capability checks still pass.
- Disabling LiP requires the intended confirmation and changes scores only after confirmation; zero-score recalculation is tested with synthetic records.
- Run both summary-page and detail-page action scenarios, because the copies are separate sinks today.

Dependencies: coordinate with the backend audit's POST/CSRF work, but removing script interpolation does not depend on database-schema or curriculum work.

### UX-02 — A failed leaderboard privacy switch silently goes back to public

**Priority:** P1. **Confidence:** high; actual JS with a rejected synthetic fetch. **Owners:** `courses/static/settings_toggles.js` and account/enrollment toggle markup.

Evidence: `courses/static/settings_toggles.js:68` saves toggles asynchronously; its failure handler at line 106 restores the previous checked state. Lines 108–114 show a visible error only for `.js-email-preference-toggle`; all other errors are console-only. The enrollment page promises immediate persistence at `courses/templates/courses/enrollment.html:264` and uses this code for public leaderboard/profile visibility at lines 269 and 283.

Reproduction: begin with a checked public-leaderboard switch, reject its POST, and click to hide the record. The browser probe observed the checkbox become checked again, with no visible failure message or live region. A timeout/expired session/server rejection can therefore leave the record public while the person believes the change was made.

Fix:

1. Give every immediate-toggle row a uniquely identified status/error container. Associate it with the input and use a live region for save/failure messages.
2. Capture the pre-change value and requested value before the request. Announce `Saving…`; on success reconcile to the returned value and announce `Saved`.
3. On rejection restore the known prior value and say plainly that the setting was not saved. For a privacy control, state that the previous visibility remains in effect; provide a retry action or an operable switch.
4. Distinguish an authentication redirect/HTML response from a valid JSON success. Guide the user to sign in again without losing the attempted choice.
5. Keep console diagnostics generic and exclude account/profile values. Reuse the status mechanism across account, enrollment, and email controls.

Acceptance tests: reject/timeout the privacy POST; return 403 and invalid JSON; verify visible and announced failure, accurate checked state, usable retry, and no false success. With delayed success, verify exactly one in-flight request and the server-returned state. Confirm that profile-form saving and immediate privacy changes do not accidentally overwrite each other.

Dependencies: none for feedback; coordinate enrollment persistence changes with the backend report.

### UX-03 — Country combobox state and keyboard activation disagree

**Priority:** P1. **Confidence:** high; actual JS. **Owners:** shared country widget and onboarding/registration browser tests.

Evidence: `courses/static/country_combobox.js:46` hides the panel without setting `aria-expanded=false`. Selection and Escape call it at lines 43 and 134. Option buttons created at line 68 stay tabbable and only handle `mousedown` at line 75; there is no click/keyboard activation handler. Only blur resets expanded state at line 141. Opening with ArrowDown at line 123 also relies on callers to set expanded state.

Reproduction: focus the country input and press Escape, or select with Enter. The panel disappears while the input still reports expanded. Type a prefix, Tab to an option, and activate with Enter; the probe did not select the country. The delayed blur can remove the focused option, adding another focus-loss path.

Impact: assistive technology receives a false popup state, keyboard users can land on an option that does not work, and mobile/switch-control click activation is not covered by a mouse-only handler.

Fix:

1. Centralize opening/closing in functions that always update panel visibility, `aria-expanded`, active option, and `aria-activedescendant` together.
2. Use the standard input-focused combobox pattern: options are not separate Tab stops (`tabindex=-1` if buttons are retained); Arrow keys change the active descendant and Enter commits it.
3. Handle click/pointer selection explicitly, preserving input focus while committing the choice. Do not depend solely on `mousedown`.
4. Make Tab close the popup and move to the next form control. Escape closes without discarding the typed value. Define ArrowUp behavior when closed.
5. Give the no-results state an appropriate polite announcement; avoid an active-descendant reference to a removed element.

Acceptance tests: keyboard open/close/select/reopen, pointer and touch-equivalent click, Tab exit, no results, and form validation with the popup open. At every transition, assert actual visibility equals `aria-expanded` and any active-descendant ID exists. Run the shared widget on both onboarding and registration at mobile and desktop sizes.

Dependencies: none. Do not change the approved country vocabulary as part of this widget fix.

### UX-04 — Learning-in-public links are unnamed form controls

**Priority:** P1. **Confidence:** high; source and actual add-link JS. **Owners:** shared field partial, add-link script, submission error renderer.

Evidence: `courses/templates/include/learning_in_public_links.html:21` uses `for="learning_in_public_links[]"`, but inputs at lines 57 and 68 have no matching ID, label, `aria-label`, or `aria-labelledby`. `courses/static/learning_in_public.js:17` creates the same unnamed input shape and does not focus the new row. `courses/static/homework.js:23` creates error elements without stable IDs or field associations.

Reproduction: render an editable submission with LiP enabled, inspect the initial URL input's accessible name, then click Add link and inspect the next input. The probe found zero associated labels and no alternative name/description for both. The visible group label is not programmatically connected to either input.

Impact: a screen-reader or voice-control user cannot reliably distinguish link 1 from link 2 or understand which link has an error. Keyboard users press Add link but remain on the button, requiring discovery of the new field elsewhere in the form.

Fix:

1. Make the group a fieldset with an appropriate legend, or retain a group heading and associate it explicitly.
2. Give each input a stable unique ID such as `learning-in-public-link-1` and a visible or screen-reader label `Learning in public link 1`. Keep the submitted name `learning_in_public_links[]` unchanged.
3. Give the shared hint an ID and reference it from every input. Render indexed errors with IDs and `aria-describedby`/`aria-errormessage` as appropriate.
4. Make JS-added rows use the same markup contract, ideally a `<template>` from the shared partial. Focus the new field after adding it and update the cap state without creating duplicate IDs.
5. When the cap is already reached on initial render, hide or disable Add link with a visible explanation instead of waiting for the first ineffective click.

Acceptance tests: initial empty/prefilled form, two dynamically added rows, cap reached, server error on one row, and client-side invalid URL. Every input must have a unique name in the accessibility tree and correct error/hint references. Verify focus moves to the new input and all submitted links remain intact after a validation failure.

Dependencies: coordinate with backend bad-link error recovery so the server returns a usable form. Shared primitive changes affect homework, project, and peer-review pages.

### UX-05 — Rejected Q&A submission hides real questions and leaves a phantom

**Priority:** P1. **Confidence:** high; actual participant script with the unchanged-response condition simulated. **Owners:** Q&A participant state/polling and browser tests.

Evidence: `events/static/events/qna/room.js:66` adds an optimistic pending item, then line 68 calls `render([], {visible: 0, answered: 0})`, discarding the displayed real list. On rejection, lines 72–74 remove the pending item from the array but do not rerender locally. `qna.js:49` deliberately skips the callback for 304 responses; the server returns 304 for the same ETag at `events/qna/views.py:203`. A rejected mutation does not need to change the question list or ETag.

Reproduction: begin with one existing question and a known ETag. Submit a new question, reject its POST, then return an unchanged 304 for the refresh. The probe observed the old question disappear and the rejected optimistic card remain rendered, while the UI said the request failed and the counts were zero. A fast second submission hitting the rate limit is one plausible trigger; the UI does not lock the submit button.

Fix:

1. Keep the latest successful server items/counts as explicit client state. A pending submission overlays that state; it must not replace it with an empty list.
2. Assign each pending operation a stable local ID. Remove or mark that specific pending item on failure and rerender immediately from cached successful state, regardless of the next network response.
3. Label pending/error states visibly. Clear a previous submission error only when appropriate and announce successful submission without erasing unrelated pending work.
4. Prevent accidental duplicate in-flight submission or implement bounded per-request tracking. Do not clear every pending operation when one POST succeeds.
5. Make refresh semantics explicit: an unchanged 304 preserves authoritative state and does not become the only way to repair an optimistic state.

Acceptance tests: existing list + successful submission; rejected 400/429/503 + subsequent 304; timeout; rapid double-click; two overlapping requests if allowed. Existing questions/counts must remain correct, a rejected item must not appear accepted, and the draft must remain recoverable. Inspect mobile/desktop screenshots of the error state.

Dependencies: coordinate with UX-06/07 to avoid conflicting edits in `room.js`/`qna.js`.

### UX-06 — Q&A list updates destroy the focused action

**Priority:** P1. **Confidence:** high for participant; equivalent host implementation inspected. **Owners:** participant and host list rendering.

Evidence: `events/static/events/qna/room.js:13` clears and rebuilds the entire list; the optimistic vote path calls that render at line 36. `events/static/events/qna/admin.js:9` and `:33` do the same for moderation. Polling applies new lists every four/five seconds when content changes.

Reproduction: focus an Upvote button and deliver an updated successful poll. In the actual-JS probe, `document.activeElement` became `BODY`. Clicking an optimistic vote/moderation action follows the same clear/recreate path before its request resolves. An active event with frequent new questions makes this a recurring barrier.

Fix:

1. Give each question row and action stable identity derived from its question ID and action name.
2. Update existing nodes in place and add/remove/reorder only changed rows. If retaining rebuilds temporarily, capture focused question/action and restore the matching control after render.
3. Define the fallback when a moderated/deleted question disappears: next relevant question action or the list heading, with a polite removal announcement. Do not blindly jump to page start.
4. Update vote count/pressed state without rebuilding unrelated controls. Put failure feedback near the action; both vote and moderation currently revert silently in their catches.
5. Ensure the same state/render helper supports participant and host without exposing host-only controls to participants.

Acceptance tests: focus survives a different question arriving, a score update, sorting, own vote completion/rejection, and another host's moderation. When the focused question is deleted, focus lands on the documented fallback. Run keyboard-only participant and host flows at both viewport sizes.

Dependencies: same Q&A batch as UX-05; keep role-specific action authorization server-owned.

### UX-07 — Q&A controls ignore lifecycle/configuration state

**Priority:** P1. **Confidence:** high source confidence; full session-transition browser reproduction remains required. **Owners:** Q&A serialization, poll response handling, and participant template.

Evidence:

- `events/qna/views.py:126` supplies `can_ask` and `can_vote`; `templates/events/qna/public.html:11` renders an enabled submission form regardless of those capabilities/state.
- `room.js:25` renders vote buttons without checking the session state.
- The questions response includes `state` at `events/qna/views.py:208`, but `events/static/events/qna/qna.js:53` passes only items/counts to consumers.
- `events/qna/services.py:844` builds the list ETag from question digests only, excluding the session state/revision. Closing a session without changing a question can therefore return 304 to an already-open participant page.
- Studio exposes default-sort configuration at `templates/studio/event_qna.html:39`, but the participant template selects Popular unconditionally at `templates/events/qna/public.html:27`; `room.js:77` passes that selection, bypassing the configured default.

Impact: a closed session still invites questions and votes that the server rejects. A session closing in another tab may continue to look Open. A configured Recent default is ignored. Poll failures also overwrite the banner (`qna.js:55`) without a clear successful-recovery update, mixing lifecycle and network status.

Fix:

1. Render initial control availability and selected sort from the server's session/capability context. Closed sessions show readable questions plus an explanation and no enabled mutation controls.
2. Return a structured poll result containing state/capabilities/items/counts. Apply state updates even when the question content is unchanged.
3. Include session revision/state and all representation-affecting data in the ETag, or separate session-state polling with its own validator. Define the contract before changing client caching.
4. Keep lifecycle status and connection/error status separate. Restore healthy connection feedback on recovery without falsely reopening a closed session.
5. Preserve an explicitly user-chosen sort; use the configured default only on initial load. Reconcile name requirements if they can change while the room is open.

Acceptance tests: initial closed session; open→closed without question changes; reopened session; expiry; unchanged ETag; connection loss/recovery; Recent configured with an explicit later user sort. Server rejection remains authoritative and every visible enabled action must be currently available.

Dependencies: a small response/ETag contract update is required; implement alongside UX-05/06. Do not relax server lifecycle enforcement.

### UX-08 — Q&A form falls back to a GET containing authored content

**Priority:** P1. **Confidence:** high; template and browser-native behavior. **Owners:** Q&A participant HTML fallback and private response handling.

Evidence: `templates/events/qna/public.html:11` has a `<form id="qna-question-form">` with no method/action. Named `text` and optional `author_name` controls occur at lines 13 and 16. The only submission interception is the listener in `room.js:61`. The browser probe reports native method `get`.

Reproduction: disable JavaScript or fail the Q&A script load, enter synthetic values, and submit. Native HTML submits the field names/values as a query string to the current page. The question is not posted through the intended JSON mutation route. The submitted text/name can enter browser history, copied URLs, and request logs. Whether downstream logs retain it depends on deployment logging; no production retention claim is made here.

Fix:

1. Give the form an explicit POST action to a supported HTML submission handler and include CSRF, or render it inactive until successful JS initialization with a clear non-JS explanation. The stronger UX is a real server-backed form.
2. The HTML handler must call the same question service/rate limits as the API, return safe form errors, and redirect after success. Never implement a second independent authorization path.
3. Preserve question text after an error without placing it in query parameters. Keep Q&A pages private/no-store/noindex as required.
4. If choosing a JS-required fallback, make that state clear in the initial HTML, not only in `<noscript>`; an enabled-browser script failure also needs a safe form state.

Acceptance tests: JS disabled, one script 404, initialization exception, and normal JS enabled. No authored text/name appears in the URL. Successful supported fallback creates exactly one question; unsupported fallback performs no request and gives a usable explanation.

Dependencies: a route is required only for the progressive-enhancement implementation; coordinate that route with the Q&A service owner.

### UX-09 — Enrollment sorting is misleading across pagination

**Priority:** P1. **Confidence:** high source confidence. **Owners:** Studio enrollment query/view/template.

Evidence: `studio_courses/views/enrollment_list.py:23` paginates the enrollment list before rendering and returns only `object_list` at line 32. `studio_courses/templates/studio_courses/enrollments.html:257` sorts only rows already in the current `<tbody>` at line 267. The page displays the total result count and ordinary sort headers (`:89`, `:124`, `:137`) without saying the sort is page-local. The server's fixed initial ordering is `position_on_leaderboard, id` at `studio_courses/views/view_models.py:140`. The arrows at template lines 309–312 never update `aria-sort`.

Reproduction: seed more than one page of students with a high scorer on page two. On page one, click Score descending. That student cannot move onto the first page because the browser never received the row. Navigate to page two and the chosen sort resets. A user looking for all highest/lowest scorers can get the wrong subset.

Fix:

1. Add allowlisted sort and direction parameters to the view; do not accept arbitrary ORM field names from the query string.
2. Apply the requested ordering after filtering and before pagination. Include a deterministic tie-breaker and explicit null-position behavior.
3. Render sort controls as GET links or a GET form that preserves search/status, changes sort, and resets the page to one.
4. Carry sort/direction through pagination links and render `aria-sort` on the active column header. The accessible control name should announce the next action.
5. Delete the duplicated client-side table sort or limit it to a documented enhancement that matches the server ordering exactly.

Acceptance tests: more than two pages, score ties, missing leaderboard positions, filtered results, switching directions, back/refresh, and JS disabled. The globally highest scorer must be first when sorting descending regardless of their previous page. Verify keyboard sorting and current sort announcement.

Dependencies: no schema change required; query performance and support-flag calculation remain a backend concern that should be measured with the large fixture.

### UX-10 — Enrollment error rendering omits the established accessible form contract

**Priority:** P1. **Confidence:** high source confidence. **Owners:** enrollment template and form rendering.

Evidence: `courses/templates/courses/enrollment.html:225` begins the form without the shared `accessibility_error_summary`. It renders raw widgets at lines 238/251 and error containers without IDs at lines 241/254. `courses/views/forms.py:105` only adds an `is-invalid` CSS class. The design contract at `_docs/design/design-system.md:555` requires a focusable summary and field-associated help/errors. The account settings page already uses these primitives at `course_platform_templates/accounts/account_settings.html:333` and `:350`.

Reproduction: cause a server-side validation error such as an overlong leaderboard display name, then inspect the rendered form. The error text lacks an explicit association to its field; the page has no shared summary to receive focus. Any Django-generated `aria-describedby` must also be checked because this template does not render Django's default error-list IDs.

Acceptance tests: invalid display name, certificate-name failure if a bounded validator applies, non-field failure, and successful retry. Error-summary links focus visible inputs, every error reference resolves, and submitted values survive. Verify mobile and desktop keyboard behavior.

Dependencies: no schema work. Coordinate backend validation behavior and avoid inventing a new certificate-name requirement in this accessibility task.

### UX-11 — Local-storage failure reverses a successfully saved theme switch

**Priority:** P2. **Confidence:** high; actual script with successful fake server response. **Owners:** account preference JS.

Evidence: `courses/static/settings_toggles.js:97` applies the saved theme, then line 103 writes local storage without a try/catch. A storage exception reaches the generic request catch at line 106, which sets the checkbox back to its previous value even though the server save succeeded and the page theme already changed. The shared signed-out theme implementation catches storage errors at `templates/core/_site_shell_foot.html:49` and `:58`, so the two persistence paths handle the same browser condition differently.

Reproduction: make a dark-mode POST return `{field: dark_mode, value: true}` while local storage is unavailable. The probe used an isolated storage-denied document and observed the unchecked switch beside an applied dark theme. This demonstrates exception ordering; reproduce on a same-origin page with a stubbed throwing Storage method for the permanent test.

Fix:

1. Treat the successful server response as authoritative. Reconcile the checkbox and page theme to that response.
2. Wrap the optional local-storage write separately. Its failure must not enter the network-save failure path or roll back the server state.
3. If storage is unavailable, retain the signed-in behavior; a signed-out preference may simply not persist across visits. Do not display a false failed-save message.
4. Use the same small storage helper in both theme paths if practical, while preserving the distinction between server-owned signed-in state and local signed-out state.

Acceptance tests: storage write throws after successful save; storage unavailable on initial load; server save fails; theme can be toggled again. Checkbox, body class, and reloaded server preference must agree.

Additional bounded follow-up: `accounts/views/account_settings.py:52` deliberately preserves immediate-toggle values on normal profile POST. If the account page is intended to support disabled/broken JS, the current enabled theme control plus Save changes is misleading because the submitted toggle is ignored. Either provide a no-JS save contract or render an explicit disabled/unavailable control. The public no-JS reading policy alone does not establish the required private-settings fallback, so this is a product-policy check, not a separately confirmed requirement violation.

Dependencies: can share UX-02's script change and tests.

### UX-12 — Studio shows Pin even when a question is already pinned

**Priority:** P2. **Confidence:** high source confidence. **Owners:** Studio Q&A moderation template.

Evidence: `templates/studio/event_qna.html:50` displays the pinned state but line 55 always submits `action=pin` with label Pin. `events/qna/studio_views.py:97` and `:98` support both pin and unpin. The separate host UI correctly chooses Pin/Unpin in `events/static/events/qna/admin.js:23`.

Reproduction: pin a synthetic question through Studio and reload. The page shows `pinned` alongside another Pin button; it offers no way to invoke the already-supported unpin action. A moderator must find another UI or use an API to undo the choice.

Fix:

1. Render `Unpin` with `action=unpin` for pinned questions; otherwise render Pin.
2. Keep capability checks and CSRF unchanged. Derive action/label from the rendered server state, not an unrelated local flag.
3. Show a visible saved/error status after the action; the current `?saved=1` redirect should have a corresponding user-visible result if this pattern is retained.
4. Add parity assertions for the supported actions in Studio and the host view. Do not add destructive restore/answer transitions without checking the service contract.

Acceptance tests: pin then unpin via Studio, stale state/repeated action, denied role, and failed service response. Label/action pair must match the current state and a moderator can undo a pin without another surface.

Dependencies: no new backend action is needed; UX-06 can share the action-state vocabulary.
